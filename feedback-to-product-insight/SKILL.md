# Feedback to Product Insight

把原始用户反馈转化为证据可追溯、边界清楚、可继续验证的产品洞察。保持问题空间与解决方案空间分离。

## 工作流程

1. 识别数据集名称、版本、日期与来源；缺失时标记 `unknown`，不得自行猜测。
2. 检查输入是否包含稳定的反馈编号；没有编号时先按数据集版本生成 `V1-F01`、`V1-F02` 等编号，并保留原文。
3. 先建立“反馈编号—原始文本”对照，再逐条提取用户明确表达的事实。
4. 合并语义相同的问题；不要为了增加证据数量而合并不同问题。
5. 从事实推断用户希望取得的进展，避免把用户建议的解决方案直接当作需求。
6. 按 [证据规则](references/evidence-rules.md) 标记结论类型、置信度和关系类型。
7. 按 [输出结构](references/output-schema.md) 记录来源元数据并生成主表。
8. 针对缺失信息，参考 [研究方法](references/research-methods.md) 给出可执行的下一步。
9. 将 P0 收敛到最多三项；其余放入 P1、P2 或研究储备。
10. 输出前执行证据与边界检查。

## 分析规则

- 引用实际存在的反馈编号；不得伪造或错误复用编号。
- 将竞品资料作为解决方案启发，不作为用户需求证据。
- 将问题表述为用户障碍、目标或需要取得的进展，不直接写成功能名称。
- 对互相矛盾的反馈分别保留，并指出需要分群或进一步研究。
- 将问题之间的并列、相关、因果假设分开；没有过程证据时不得使用确定性因果表达。
- 对没有行为数据、市场数据或价格信息的问题明确写“无证据”。
- 将样本内置信度与市场普遍性分开；不得用小样本证明总体需求。
- 让研究方法直接回答对应的缺失信息，避免笼统地写“进一步调研”。

## 输出要求

默认输出 Markdown 表格。用户要求批量处理、系统导入或 MCP 传递时，改用 `references/output-schema.md` 中的 JSON 结构。

输出顺序：

1. 来源元数据。
2. 样本与分析限制。
3. 需求洞察主表。
4. 矛盾证据、潜在用户分群或未经验证的关系假设。
5. P0/P1/P2 专项调研清单。
6. 当前材料明确无法回答的问题。

## 输出前检查

- 每条推断是否有真实证据编号？
- 是否记录了数据集名称、版本、日期和来源？
- 证据是否直接支持该问题，还是仅弱相关？
- 是否把用户提出的功能方案误写成真实需求？
- 是否把竞品功能误写成用户证据？
- 置信度是否同时考虑证据数量、直接性、一致性和反证？
- 缺失信息是否具体且会影响决策？
- 下一步研究能否补足对应信息？
- 是否把相关性、并列关系或可能路径错误写成确定因果？
- P0 是否不超过三项，并确实影响 MVP 价值或安全边界？
- 是否明确标出无证据结论？
